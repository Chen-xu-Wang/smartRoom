# 百炼手工搭建指南（三个应用 + 一个知识库）

> 版本：v1.0（2026-09-20）。对应比赛 2.2「技术方案」中"如基于平台搭建，说明使用的平台名称、平台能力之外自己做了哪些设计"。
> 平台：**阿里云百炼（Model Studio）**，地域 **华北2（北京）**（知识库目前只在北京地域可用）。
> 本指南只写"在控制台点哪里、填什么"；为什么这么填见每步后面的「为什么」。

## 〇、整体流程（用户输入 → 最终结果）

```
传感器/模拟器 ──► 检测算法（自研，Python）
                     │  产出 契约① 事件 JSON
                     ▼
        ┌────────── 百炼应用① 事件解读（工作流应用）──────────┐
        │ 开始节点 event_json                                  │
        │   ▼                                                  │
        │ 知识检索节点 ──► 住宅运维知识库（5 本手册）          │
        │   ▼                                                  │
        │ 大模型节点（qwen-max + 系统提示词 + 2 个 few-shot）   │
        │   ▼                                                  │
        │ 结束节点：契约② 事件决策 JSON                        │
        └──────────────────────────────────────────────────────┘
                     │
                     ▼
   后端 FastAPI 校验（JSON Schema + 决策规则兜底）──► 落库
                     │
        ┌────────────┼─────────────┬────────────────┐
        ▼            ▼             ▼                ▼
   住户提醒     邻户/家属提醒    物业工单      控制动作建议
   （App 推送）                （智能派单）   （人工确认后执行）

另有两个应用走同样的"输入 JSON → 大模型 → 输出 JSON"结构：
  应用② 月度报告：契约③ 聚合 JSON → 报告 JSON（住户月报 / 批次简报）
  应用③ 水电问答：契约④ 上下文 JSON + 住户问题 → 回答 JSON（带 evidence 溯源）
```

**平台之外自己做的部分**（评审重点问这一项）：

| 自研部分 | 位置 |
| --- | --- |
| 数据契约（4 组 JSON Schema） | `data/processed/contracts/` |
| 异常检测与定位算法、物理模拟器 | `data/scripts/sim/`、`data/scripts/run_*.py` |
| 知识库正文（5 本手册） | `backend/app/data/knowledge/` |
| 三份系统提示词与 few-shot | `prompts/` |
| 输出的 Schema + 决策规则自动校验 | `data/scripts/validate_contracts.py` |
| 批量回归调用脚本 | `data/scripts/call_bailian.py` |
| 后端落库、派单、SLA、前端四端界面、3D 数字孪生 | `backend/`、`frontend/`、`3D/` |

百炼负责的只有"把结构化证据翻译成分角色的人话与结构化决策"这一段，检测、校验、执行都在自研代码里。

## 一、准备工作

1. 登录 [百炼控制台](https://bailian.console.aliyun.com)，右上角地域切到 **华北2（北京）**。
2. 开通模型服务，确认 `qwen-max`（或 `qwen-plus`）可用。
3. 左侧「API-KEY」→ 创建 API Key，保存 `sk-` 开头的串，填到 `backend/.env` 的 `BAILIAN_API_KEY`。

---

## 二、建知识库（只给应用① 用）

1. 左侧「数据管理 → 数据中心（非结构化数据）」→ **导入数据** → 本地上传 `knowledge/upload/` 下的 5 个 md 文件。
2. 左侧「知识库」→ **新建知识库**：
   - 名称：`筑维AI-住宅运维知识库`
   - 类型：**文档搜索**（非结构化）
   - 选中刚导入的 5 个文件
3. 解析与切分：
   - 切分方式：**按标题层级**（无此选项时选"智能切分"或长度切分，长度 500、重叠 100）
   - 向量模型：保持平台默认的中文 embedding 模型
4. 检索配置（建库后在知识库详情里调，也可以在应用的知识检索节点里覆盖）：
   - 召回数量 **5**，相似度阈值 **0.2**，**开启 rerank**
5. 用知识库自带的「命中测试」输入下面几句，确认召回的是对应章节：
   - `厨房回路断路器端子温度92℃` → 期望命中 `主动运维补充-端子发热处置`、`电气维修手册-配电箱跳闸`
   - `花洒出水变小 水垢` → 期望命中 `给排水维修手册-卫生间花洒出水异常`
   - `独居老人上午没有活动信号` → 期望命中 `主动运维补充-独居守护分级响应`

**为什么**：手册按"## 章节"组织，按标题切分能让"常见原因—判断依据—处置—安全提示"留在同一个块里，模型拿到的是完整处置逻辑而不是半句话；阈值压到 0.2 是因为"爆管""暗漏"这类词在手册里字面出现少，阈值高了会直接召回为空。

---

## 三、应用① 事件解读（工作流应用）

「应用 → 新增应用 → **工作流应用**」，命名 `筑维AI-事件解读`。

### 3.1 开始节点

新增输入变量：

| 变量名 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `event_json` | String | 是 | 契约① 事件 JSON 的**字符串**形式 |

**为什么用 String 而不是 Object**：调用方 `call_bailian.py` 用 `json.dumps` 把整个事件序列化后放进 `biz_params`，一个变量就能传完整证据，节点之间也不会因为嵌套对象的类型校验而报错。

### 3.2 知识检索节点

- 知识库：选第二节建的 `筑维AI-住宅运维知识库`
- 检索内容（query）：引用开始节点的 `event_json`
  （更省 token 的做法：先加一个"文本处理/参数提取"节点，只取 `event_type`、`evidence_text`、`location_candidates[].segment_name` 拼成一句话再检索）
- 召回数量 5，阈值 0.2，rerank 开

### 3.3 大模型节点

- 模型：`qwen-max`
- Temperature：**0.01**，Top-p 默认（要的是稳定的结构化输出，不要创造性）
- 最大回复长度：拉到 **2048 以上**（样例 04 的批次工单带 25 个户号，输出较长）
- 系统提示词（System）：整段粘贴 `prompts/app1_event_system_prompt.txt`
- 用户提示词（Prompt）里插入两个变量，**在输入框里敲 `/` 从下拉里选变量**，不要手打变量名（不同版本的变量表达式写法不一样，手打容易引用不到）：

```
# 知识库检索结果
/（插入 知识检索节点 的 result）

# 待处理事件
/（插入 开始节点 的 event_json）
```

- 输出格式：如果模型节点有「JSON 输出」开关，可以开；开了之后结束节点拿到的是对象，没开就是字符串，两种 `call_bailian.py` 都能解析。

> 小标题 `# 知识库检索结果`、`# 待处理事件` 要和系统提示词「# 输入」一节里写的**一字不差**，模型靠这两个标题区分"经验"和"事实"；改了标题就要同步改提示词。

### 3.4 结束节点

- 输出模式：文本 / JSON 均可，直接引用大模型节点的输出，**不要再套一层解释文字**。

### 3.5 试运行

在右上角「测试」里，`event_json` 粘贴 `events/03_terminal_overheat_1302_kitchen_circuit.json` 的全文，检查输出是否满足：`priority=URGENT`、工单工种为电工维修、安全提示同时含"验电"和"挂牌"、`knowledge_refs` 里出现 `主动运维补充-端子发热处置`。

## 四、应用② 月度报告、应用③ 水电问答

同样用**工作流应用**，但**不接知识库**（这两个应用的回答只能来自输入的聚合数据，接知识库反而会诱导模型引入手册里的通用说法）。

| 项 | 应用② `筑维AI-月度报告` | 应用③ `筑维AI-水电问答` |
| --- | --- | --- |
| 开始节点变量 | `report_json`（String） | `qa_json`（String） |
| 节点链路 | 开始 → 大模型 → 结束 | 开始 → 大模型 → 结束 |
| 系统提示词 | `prompts/app2_report_system_prompt.txt` | `prompts/app3_qa_system_prompt.txt` |
| 用户提示词小标题 | `# 待生成报告的数据` | `# 问答上下文` |
| 模型 / 温度 | qwen-max / 0.01 | qwen-max / 0.2（口语化一点） |
| 测试输入 | `monthly/01_*.json`、`batch_brief/01_*.json` | `qa/01_*.json` |

用户提示词照这个格式写，变量同样用 `/` 插入：

```
# 待生成报告的数据
/（插入 开始节点 的 report_json）
```

> 应用③ 如果要做成真正的多轮问答（住户连着追问），调用时带上 `session_id` 让平台托管上下文，或者由后端把历史 `messages` 一起传；问答上下文 `qa_json` 每轮都要重新传，因为它是数据而不是对话历史。

## 五、发布与接入

1. 每个应用右上角 **发布**。
2. 「应用 → 发布渠道 → API」里拿到 **APP_ID**，填进 `backend/.env`：

```
BAILIAN_API_KEY=sk-xxxx
BAILIAN_APP_EVENT=事件解读的APP_ID
BAILIAN_APP_REPORT=月度报告的APP_ID
BAILIAN_APP_QA=水电问答的APP_ID
BAILIAN_BASE_URL=https://dashscope.aliyuncs.com
```

3. 批量回归（会把输出存到 `runs/<app>/` 并按契约校验）：

```bash
python data/scripts/call_bailian.py --app event
python data/scripts/call_bailian.py --app report
python data/scripts/call_bailian.py --app qa
```

4. 单份输出手工校验：

```bash
python data/scripts/validate_contracts.py --contract event_decision --file data/processed/bailian_kit/runs/event/03_terminal_overheat_1302_kitchen_circuit.output.json --event data/processed/bailian_kit/events/03_terminal_overheat_1302_kitchen_circuit.json
```

调用协议：`POST /api/v1/apps/{APP_ID}/completion`，开始节点变量通过 `input.biz_params` 传，值是 JSON **字符串**（见 `data/scripts/call_bailian.py:call_app`）。

## 六、验收标准

百炼输出**不要求与 `expected/` 逐字一致**，要求：

1. 能通过 `validate_contracts.py` 的 Schema 校验；
2. 满足 `data/processed/contracts/README.md` 第五节的决策规则（带 ★ 的已做成自动检查）；
3. 文案里每个数字都能在输入 JSON 里找到出处；
4. `knowledge_refs` 引用的章节在知识库里真实存在。

提示词里嵌了样例 01、03（应用①）、月报 01（应用②）、问答 01（应用③），**这几个只能用来看回归有没有退化，检验泛化要看 02、04、05 这些没进提示词的样例。**

## 七、常见问题

| 现象 | 原因与处理 |
| --- | --- |
| 输出被 ```` ```json ```` 包住，或前面多一句"好的，以下是…" | 提示词铁律已写明"不要包裹"，仍出现时把温度降到 0.01；`call_bailian.py` 的 `extract_json` 也会兜底剥壳 |
| 结束节点返回 `{"result": "{...}"}` 这类单键套娃 | 结束节点选了 JSON 输出模式，正常现象，脚本已兼容 |
| 调用报找不到知识库 / 应用 | 地域不对，确认应用、知识库、base_url 都在华北2（北京） |
| `knowledge_refs` 里出现手册里没有的章节名 | 知识检索节点没接上或召回为空，模型在凭记忆编；先去命中测试确认召回，再检查提示词里是否真的插入了检索结果变量 |
| 批次样例（04）输出被截断 | 大模型节点的最大回复长度调大到 2048 以上 |
| 住户文案里出现"P90""百分位""剩余电流" | 提示词的术语黑名单没生效，检查系统提示词是否完整粘贴（app1 共 91 行，结尾是示例 2 的输出） |
